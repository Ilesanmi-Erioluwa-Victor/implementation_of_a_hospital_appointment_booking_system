- ONE UNAVOIDABLE TECHNICAL NOTE: connecting to MongoDB from PHP
  requires the `mongodb` PHP extension (installed via PECL) to be
  present in whatever environment actually RUNS the PHP code — this
  is a runtime requirement of the language/driver, not a "local
  database install." On Render, use a Docker-based PHP environment
  where the `mongodb` extension is installed inside the Dockerfile
  (in the deployment environment, not on the developer's personal
  machine). Prefer testing the running app via deployment (Render) or
  a cloud dev container/environment rather than installing PHP plus

You are building "MediBook" — a hospital appointment booking system
for a Nigerian polytechnic/university final year project, using Delta
State Teaching Hospital as the case study. The system replaces manual
appointment booking (long waiting times, conflicts, poor record
management, delays) with a computerized platform where patients
register, log in, view available doctors, book appointments, and
receive confirmations, while hospital administrators manage doctors,
appointments, and reports. Follow this spec exactly, and follow the
IMPORTANT CONSTRAINTS above without exception — nothing about this
project should require installing a database, mail server, or other
non-essential software on the developer's local machine. Build
incrementally, one module at a time, confirming each works before
moving to the next.

PROJECT GOAL
-------------
A secure, reliable, user-friendly web platform automating the
appointment scheduling process end-to-end: patient registration and
login, doctor/department browsing, real-time availability-aware
booking, appointment confirmation, and administrative reporting —
minimizing paperwork and scheduling conflicts, and improving
communication between patients and healthcare providers.

DATABASE COLLECTIONS (MongoDB documents)
--------------------------------------------
patients
  _id, firstName, lastName, email (unique), phone (unique), gender,
  dateOfBirth, address, passwordHash, isEmailVerified,
  createdAt, updatedAt, deletedAt (soft-delete for account closure)

departments        (specializations — e.g. "Cardiology",
                      "Pediatrics", "General Outpatient")
  _id, name, description, createdAt, updatedAt

doctors
  _id, firstName, lastName, email, phone, departmentId (ref:
  departments), bio, photoUrl, isActive: bool,
  workingHours: [
    { dayOfWeek: 0-6, startTime: "09:00", endTime: "16:00" }
  ],   // the doctor's normal weekly schedule
  slotDurationMinutes: number (e.g. 30),  // how long each bookable
                                            // appointment slot is
  createdAt, updatedAt

scheduleExceptions   (a doctor's leave/unavailable dates, or a
                       special extra clinic day — kept as its OWN
                       collection so a doctor's whole workingHours
                       array doesn't need editing for a one-off change)
  _id, doctorId (ref: doctors), date, type: "unavailable"|
  "extra_availability", overrideStartTime, overrideEndTime, reason,
  createdAt

staffUsers        (admin, front-desk/receptionist)
  _id, name, email (unique), passwordHash,
  role: "admin"|"front_desk", createdAt, updatedAt

appointments
  _id, patientId (ref: patients), doctorId (ref: doctors),
  departmentId (ref: departments),
  appointmentDate (Date, date-only portion),
  timeSlot (e.g. "10:00-10:30" — string or structured
  { start, end }),
  status: "pending"|"confirmed"|"completed"|"cancelled"|"no_show",
  reasonForVisit, bookedByType: "patient"|"front_desk" (front-desk
  staff can book on behalf of walk-in patients),
  bookedByStaffId (ref: staffUsers, nullable),
  confirmedAt, cancelledAt, cancelReason, completedAt,
  createdAt, updatedAt

reminderLogs      (prevents duplicate reminder emails — same pattern
                    as any scheduled-job system)
  _id, appointmentId (ref: appointments), sentAt,
  reminderType: "24h_before"|"2h_before", status: "sent"|"failed"

Indexes to create in MongoDB Atlas:
  - patients.email (unique), patients.phone (unique)
  - staffUsers.email (unique)
  - appointments: UNIQUE compound index on (doctorId, appointmentDate,
    timeSlot) EXCLUDING cancelled status — MongoDB doesn't support a
    partial-unique-index-with-status-exclusion quite as simply as SQL,
    so implement double-booking prevention primarily at the
    application/service layer (check-then-insert inside a
    transaction, or use MongoDB's `findOneAndUpdate` with an
    upsert-style guard) AND add a compound index on (doctorId,
    appointmentDate, timeSlot) for fast lookup even if it isn't
    strictly unique — document this design decision clearly in
    Chapter 3
  - appointments: compound index on (patientId, appointmentDate) for
    a patient's own appointment history queries
  - scheduleExceptions: compound index on (doctorId, date)

CORE FEATURES — COVER EVERY SCENARIO BELOW
----------------------------------------------

1. AUTHENTICATION
   - Patient register/login, bcrypt password hashing
   - Email verification via Brevo before booking is allowed (or at
     minimum before confirmation emails are trusted to reach them)
   - Staff (admin/front-desk) login, separate from patient login
   - Password reset flow with a single-use, time-limited token
   - Rate limiting on login/register/password-reset endpoints
   - CSRF protection on all state-changing form submissions

2. DEPARTMENTS & DOCTOR DIRECTORY
   - Admin manages departments/specializations
   - Admin manages doctor profiles: bio, photo, department, weekly
     workingHours, slotDurationMinutes, active/inactive status
   - Patients can browse doctors by department, view bio and general
     weekly availability pattern before booking
   - Deactivating a doctor (e.g. they've left the hospital) must NOT
     delete their historical appointment records — mark inactive, keep
     history intact, and prevent new bookings against them

3. AVAILABILITY-AWARE BOOKING (the core feature — cover every
   scenario)
   - When a patient selects a doctor and a date, compute the list of
     BOOKABLE time slots by:
     a. Starting from the doctor's workingHours for that day of week
     b. Slicing into slotDurationMinutes chunks
     c. Removing any slot already taken by an existing non-cancelled
        appointment for that doctor/date
     d. Removing the whole day if a scheduleExceptions entry marks it
        "unavailable" (leave/holiday), or applying an
        "extra_availability" override if present
     e. Removing past time slots if the selected date is today
   - Never let the frontend alone decide which slots are free — the
     backend must re-validate availability at the moment of booking
     submission (race condition: two patients viewing the same
     "available" slot at once) and reject with a clear "this slot was
     just taken, please choose another" error rather than creating a
     double-booking
   - Booking creates an appointment with status "pending" (or
     "confirmed" immediately if you choose auto-confirm — document
     your choice; a hospital front desk may want a manual confirmation
     step for certain departments)
   - On successful booking, send a confirmation email via Brevo
     with the appointment details (doctor, department, date, time,
     a cancellation link/reference)

4. APPOINTMENT MANAGEMENT (patient side)
   - View upcoming and past appointments
   - Cancel an appointment — enforce a minimum notice window (e.g. no
     cancellation within 2 hours of the appointment time) with a clear
     message if the window has passed, encouraging them to call the
     hospital directly instead
   - Reschedule: implemented as cancel-old + book-new against the
     availability engine (reuses the same validation logic, avoids a
     separate "reschedule" code path with its own bugs)
   - View department/doctor details again from an existing appointment

5. APPOINTMENT MANAGEMENT (staff side)
   - Front-desk can book an appointment on behalf of a walk-in patient
     who isn't registered online yet — either look up an existing
     patient record by phone/name or quickly create a minimal patient
     record inline
   - Admin/front-desk dashboard: list/search/filter all appointments by
     date, doctor, department, status, patient name
   - Mark an appointment "completed" after the visit, or "no_show" if
     the patient didn't turn up — this status distinction matters for
     the no-show reporting feature below
   - Cancel an appointment on the hospital's side (e.g. doctor
     emergency) -> this MUST trigger a notification email to the
     affected patient(s), not just a silent status change
   - Bulk-cancel/reassign all of one doctor's appointments for a given
     date (e.g. doctor called in sick) — notify every affected patient
     in one operation, don't make staff cancel one by one

6. REMINDERS (scheduled job)
   - A scheduled job (Render Cron Job or an external trigger hitting a
     protected `/cron/send-reminders` endpoint every 15-30 minutes)
     scans for upcoming confirmed appointments crossing a reminder
     threshold (e.g. 24 hours before, 2 hours before) and sends a
     reminder email via Brevo
   - Log every sent reminder in reminderLogs immediately so a cron
     overlap/retry never sends a duplicate
   - Skip reminders for appointments already cancelled/completed by
     the time the job runs

7. REPORTING (the abstract's stated "reports efficiently" feature)
   - Appointments per doctor / per department over a date range
   - No-show rate per doctor/department (no_show count / total
     appointments count)
   - Busiest time slots / days (useful operational insight for the
     hospital)
   - Cancellation rate and common cancellation reasons
   - Exportable as CSV/PDF for hospital administrators who need
     offline copies

8. RESPONSIVE UI (Bootstrap, per the approved abstract)
   - Patient-facing pages: register/login, doctor directory (filter by
     department), booking flow (date picker -> available slots ->
     confirm), my appointments, profile
   - Staff-facing pages: admin dashboard, doctor/department management,
     appointments list with filters, reports view
   - Mobile-responsive using Bootstrap's grid/components — test at
     common breakpoints

EDGE CASES TO EXPLICITLY HANDLE
------------------------------------
  - Two patients attempt to book the exact same doctor/date/slot at
    the same moment -> backend re-validation at submission time
    rejects the second one with a clear, friendly error, not a silent
    duplicate or a raw DB error
  - A doctor's workingHours change AFTER appointments already exist
    for future dates under the old hours -> already-booked
    appointments remain valid (they were booked against real
    availability at the time); only NEW bookings use the updated
    hours. Don't retroactively invalidate existing appointments
    because a schedule changed later
  - A doctor is marked on leave (scheduleExceptions) for a date that
    already has confirmed appointments -> this requires the bulk
    cancel/reassign flow (section 5) with mandatory patient
    notification, not a silent conflict
  - Patient tries to book an appointment for a past date/time -> reject
    before it reaches the availability engine, with a clear message
  - Patient cancels within the no-cancellation window -> block with a
    clear message rather than silently allowing or silently failing
  - Front-desk creates a walk-in booking for a patient who turns out to
    already have an account (duplicate phone/email) -> search/match
    existing patient records before creating a new one, to avoid
    fragmenting one person's history across two patient documents
  - Appointment marked "completed" or "no_show" retroactively edited
    by mistake -> allow staff correction but keep it auditable (a
    simple updatedAt + who-changed-it note is sufficient scope for
    this project; a full audit log is optional here since this system
    is lower-stakes than an academic records/grading system)
  - Very long doctor bio/notes -> truncate with "read more" in list
    views rather than breaking layout
  - Department deleted while doctors are still assigned to it -> block
    deletion (or require reassigning doctors first), never silently
    orphan doctor records
  - Patient account soft-deleted (account closure) while they have
    future appointments -> either auto-cancel those appointments (with
    notification) or block account deletion until they're resolved —
    pick one, document it, and make sure it's not just left dangling
